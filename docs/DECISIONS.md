# Current implementation decisions

- PostgreSQL 18 is the supported database and the version configured in Compose and CI. The desktop shell and browser share the Fastify API. `baloch_owner` provisions and migrates the schema. `baloch_app` runs the API with restricted grants. Old migrations stay immutable and new schema changes use the next number.
- The journal is the single source for actual balances. Store whole PKR as bigint on journal lines. The posting service validates integer amounts, active account codes and balanced sides in one transaction. Deferred database checks reject unbalanced vouchers. Journal lines are append-only. Voucher updates can only void posted originals and the trigger timestamps the change. Voids and paired reversals remain visible in transaction history. Effective balances exclude that cancelling pair.
- Master records in `partners` own partner identity. Project links reference master IDs. Legacy project-local names are matched after trimming and case folding, then parcel and feasibility references are rewritten. One active master name is allowed per normalized name. A missing commitment is displayed as unplanned; all contributions against it count as extra, with zero pending. For planned commitments, pending and extra are separately clamped at zero.
- Land parcels and building details, floors and unit types are stored in `projects.details` JSON. Parcels refer to the master partner or seller and linked files in `project_files`. The standalone historical purchase reader remains available. New parcel edits use the project site endpoint.
- Feasibility is a plan in the project JSON. Its ranges and returns are calculated on demand. Building-to-sales sync requires a preview and rejects changes to an approved baseline. It preserves rates and sold percentages on matching rows. Project funding and ledger data remain separate from plan figures.
- The demo seed uses the same funding posting service as the app. Stable demo IDs allow a repeat run without duplicate vouchers. Use an isolated local database for verification.
- Sign-in uses normalized usernames, Argon2id and opaque HttpOnly cookie sessions. Mutations require the app's CSRF request header. The app locks on hiding or suspension and the API checks the heartbeat timeout.

## Land acquisition and funding

Migration 023 adds immutable purchase agreements, payments with split sources, related costs and partner land contributions. Runtime UPDATE/DELETE grants are revoked. The SECURITY DEFINER `void_land_record` function only voids a record after its voucher has a reversal. A deferred trigger checks that payment source amounts equal the original voucher's Land Payable debit; no payment-total or balance column is stored. Migrations 001–022 are unchanged.

All writes use `postVoucher` / `voidVoucher` and the audit helper inside the same transaction. A project-row lock serializes land posting and funding edits. Purchases debit 1400 and credit seller payable 2010. Seller instalments debit 2010; related costs debit 1400. The credit is Bank 1010, Cash 1000, partner/Owner capital 3000, or lender liability 2300. Partner land contributions debit 1400 and credit 3000 with no seller/payable. Source rows are payment inputs; balances and displayed totals come from effective journal vouchers (posted originals, excluding void/reversal pairs).

Direct partner/Owner payments and costs appear once in the Partners contribution totals and Money in history with purpose Land. Funding received earlier in bank/cash remains its original capital posting; a later bank/cash seller payment never credits capital again. An optional loan-funding link identifies the lender's loan but represents an additional direct disbursement; money already in bank/cash must be paid using that bank/cash source.

The service rejects overpayment, insufficient project bank/cash, unlinked direct partners, invalid lenders, fractional/non-positive rupees and dates beyond tomorrow. Edits reverse the old voucher and post a replacement atomically. Stale or already-void records return 409. Purchase edits/voids require payments **and linked costs** to be void first, avoiding orphaned costs on a superseded agreement. Costs without a purchase are project-wide, including costs associated with contributed land. Changing the acquisition/contact on a parcel with posted land records is blocked until those records are voided.

Routes: `GET /api/projects/:id/land`; POST/PUT/POST-void under `purchase`, `payments`, `costs`, and `contribution`. Reads require project and ledger access; writes require manageProjects. The read model supplies all histories, per-parcel/project figures, source percentages and available funds. Transactions links filter by voucher ID.

The idempotent demo posts a 6 Cr purchase, 3.5 Cr instalments (Bank 2.6 Cr, AP 40 L, Owner 50 L), 35 L related costs, and a separate AP contribution of land worth 1 Cr. An extra 1 Cr bank funding entry prevents negative funds. Combined land asset = 7.35 Cr; payable = 2.5 Cr. Posted demo records are not rewritten on rerun.
