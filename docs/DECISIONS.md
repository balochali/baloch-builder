# Decisions — Phase 1

- The revised request supersedes the original monorepo and replacement-shell proposal. Keep the frontend in `src/`; the only npm workspace packages are `server/` and `shared/`.
- Preserve the developed `dev` design. At the initial Phase 1 start, local references showed the Tauri scaffold (`c486a95`). Task 1 fetched remotes and confirmed developed `origin/main` at `e3a29ba`; local `main` remains stale and untouched. Existing design-lock hashes remain unchanged. Protected files and baseline hashes are listed in REWRITE_PLAN.md and DESIGN_LOCK.json. Keep existing login wording, including “Username” (enter the server email in that field) and its local-storage footer, to honor the explicit wording lock; the README explains that server records live in PostgreSQL.
- Use opaque, random server-side sessions: eight-hour expiry, SHA-256 token hashes, HttpOnly/SameSite Strict cookies, Secure cookies in production. Mutation requests require a custom CSRF header; the server does not enable cross-origin access. Serve frontend/API from one HTTPS origin.
- Passwords use Argon2id. Login is limited to five attempts per minute per client IP plus normalized email, with an independent thirty-attempt per-IP cap. Privileged users can enroll TOTP; secrets use AES-256-GCM with a deployment key and accepted time steps cannot be replayed.
- PKR values are bigint paisa internally and nonnegative integer strings over JSON. Existing SQLite money remains whole rupees until the Phase 6 importer explicitly multiplies by 100.
- Number vouchers only when posting succeeds, using a transactional counter per type and fiscal-year start year. Drafts use UUIDs. Rollback does not consume a number. Serialize accounting writes and period close with one database advisory transaction lock initially; this prioritizes correctness over throughput.
- Default financial year starts in July. Its start month can change before first posting; later changes require a separate migration/review to avoid ambiguous numbering.
- Default settings: handover revenue, saleable-area cost allocation (sale-value option available), fixed project partner shares, commission as expense, tax out of scope, PKR, square feet, 272.25 square feet/marla and 20 marla/kanal. Reserved choices that require later accounting engines remain constrained to supported values.
- Until Phase 2, all BPV/CPV posting and every cash/bank credit are rejected by PostgreSQL, regardless of voucher type or role. This includes transfers and receipt reversals. Receipt posting is allowed by default; enabling receipt approval blocks those postings until approval is implemented. Threshold and single-admin settings are reserved for Phase 2 and never bypass the Phase 1 payment block.
- Reversals are new drafts referencing the original. Posting requires an exact dimensional offset. Corrected vouchers separately link to the original. Posted records and audit entries cannot be updated or deleted.
- Attachments are immutable files referenced by UUID metadata. Add them to open-period drafts; posted attachments cannot be replaced. Allowed uploads are PDF, PNG, JPEG and text, at most 10 MiB; downloads are forced attachments with nosniff.
- AG Grid Community provides editing/filtering/sorting. Clipboard paste and ExcelJS export are implemented locally without Enterprise APIs. Money cells export as exact displayed strings to avoid Excel's 15-digit precision loss. Saved views belong to the current server user.
- Unfinished modules are hidden from server navigation until their phase. The old repositories/features remain intact and the existing desktop mode remains available for historical data. No legacy SQLite data is silently read into PostgreSQL.
- The Tauri shell remains. Phase 6 retires the Rust Google Drive backup only after importer reconciliation; it does not retire Tauri.

## Task 1 stabilization decisions

- Use fixed database identities: baloch_owner owns the dedicated database/schema/tables/functions and runs only migrations/restores; baloch_app runs the server and owns none. Both roles are non-superusers, with no createdb/createrole/bypassrls privileges or inherited memberships. Runtime startup rejects an unsafe identity. Provisioning requires a separate administrator and supports explicit adoption of the existing dedicated public schema; no ledger rows are modified by ownership transfer.
- Grant the app SELECT/INSERT/UPDATE on mutable business tables, SELECT/INSERT on audit and attachments, SELECT on migration history, and DELETE only on sessions. Do not grant DDL or TRUNCATE. Trigger functions stay SECURITY INVOKER. Owner-specific default privileges cover future business tables; every new append-only table must revoke UPDATE in its creation transaction. Backups use SELECT via the app role; empty-database restores use OWNER_DATABASE_URL.
- TRUST_PROXY defaults off. Accept a bounded hop count or explicit IP/CIDR list; reject unrestricted booleans/wildcards. Prefer address lists and firewall direct backend access. A trusted-hop deployment must have the same controlled proxy chain on every path. Login budgets remain process-local; shared rate-limit storage is required before horizontal scaling.
- Verify unknown-user passwords against a dummy Argon2id hash with the same parameters, and verify inactive-user hashes as well. Do not audit unauthenticated non-login requests. Only limiter-accepted login failures may be audited, with email length capped at 254.
- A non-login 401 clears the frontend session state and returns to AuthPage. Preserve AuthPage entirely: the user chose the exact expiry message beside it instead of adding an error prop. Initial anonymous visits and failed login attempts do not produce expiry notices. Cleanup expires database sessions at startup and on accepted login attempts, supported by an expiry index.
- Use a multi-stage Node 24 image, a non-root node user and explicit attachment ownership. tsx is a runtime dependency. Docker container administration can inspect its migration credentials, although the start command unsets OWNER_DATABASE_URL before launching the app; a separate migration job is the stronger deployment option when that boundary is required.
- Preserve the historical c1b423f commit. docs/CHANGES.md inventories all 82 paths, distinguishes earlier sales work, and records that Task 9 will rebuild sales on the new ledger. No Phase 2 or sales-ledger work is included here.

## Task 2: project profiles and cost tagging

- A cost head is an analytical tag with an optional default account, never a replacement for the chart of accounts. Choosing a head fills only an empty account cell. Parent heads have at most one child level. Heads are deactivated, never deleted; codes freeze after any voucher line references them. Budget-only heads cannot tag vouchers.
- Projects start in planning. Admin can move forward or backward through handover; backward moves require a written reason. Closing and reopening closed projects are reserved for Task 10. Every actual transition has append-only history with actor, time and reason.
- Archive is independent of status. Archived projects are hidden by default and reject new draft lines and posting of existing drafts. Unarchive restores eligibility; other accounting checks still apply.
- Sales and Construction read only actively assigned projects. Assignment removal takes effect on the next API request. Only Admin manages active-user assignments and project identity/profile fields; Accountant edits allocation/revenue settings only.
- Store areas as exact PostgreSQL numeric square feet and decimal strings in the API. Shared BigInt conversion uses configurable marlaSqft (default 272.25); one kanal is always 20 marla. Admin selects sqft/marla/kanal display globally in Settings. Nonterminating converted displays round to 12 decimal places; unchanged cells never rewrite the original exact square feet. Changed cells store the exact conversion of the entered decimal.
- Saleable area versus covered area is an API validation, not a database constraint: plots may leave covered area unset. Date order and nonnegative finite areas also have database checks.
- Seeding requires the existing active bootstrap Admin credentials after initial setup. It inserts missing reference rows without resetting users, passwords, settings, accounts or edited head values. System heads have stable seed keys, so renaming an unused code does not create duplicates.
- Migrations 006–010 extend the schema without altering migrations 001–005. Existing projects receive type other, city Unspecified and status planning; Admin must review those placeholders. Invalid/duplicate legacy project codes stop migration rather than silently rewriting identifiers. Migration 009 temporarily disables only the account edit guard inside the owner migration transaction to backfill WIP flags; runtime cannot disable triggers and audit remains enabled.
- Existing posted entries are not rewritten to add cost tags. An old untagged WIP posting cannot currently have an exact reversal posted under the new mandatory-tag rule; a reviewed legacy correction policy remains necessary. Deactivated heads on posted entries remain readable; reactivate a head before using it on a reversing draft.
- Buildings may be removed only when foreign keys allow it. A future Units migration must reference project_buildings with restrictive deletion semantics; this task does not create Units.
- Task 2 adds a narrow DELETE grant for project_buildings, guarded by Admin authorization and audit. Cost heads retain the default no-DELETE grant; status history receives only SELECT/INSERT. No app table receives DDL or TRUNCATE.
- The session expiry notice is fixed to the viewport in router.tsx. AuthPage and protected styling remain unchanged.
